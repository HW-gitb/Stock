# A-short theme forward comparison adjudication

## Authority and boundary

`presets/a_short_theme_forward_comparison_governance_20260725.json` is the sole frozen policy authority. The comparator is comparison-only: it never changes P4a, official `final_score`, admission, M6.7 action, cash allocation, or production selection. A supported result is historical evidence for a separate reviewed activation route only.

## Frozen family

Seven policy-vs-primary tests use the same weekly tracker cohort, unchanged `final_score` ordering, five fixed slots, T+1 net 10-day percentage-point returns, and cash for every unfilled or known-unbuyable slot. Reports put `industry_trend` first, then `business_role`, `industry_heat`, `persistence`, `theme_breadth_pass`, `theme_fit_pass`, and `theme_heat`.

`predictive_discrimination` is a stock-only diagnostic. The actionable family is only the seven policy-vs-primary tests. Holm controls that seven-test family and Bonferroni simultaneous bootstrap intervals control the familywise interval coverage; MDE/additional-block estimates use the same family alpha and frozen 80% power target. Unadjusted values are exploratory. Each policy first creates one immutable non-overlapping evidence-block set; statistics, deployability and both challenger/primary execution profiles derive from that same set. Every counted block must contain at least three actually entered challenger positions; thin weeks remain in fixed-slot return, but cannot be hidden by a separate all-week coverage average. The overheat/chasing policy is a separate negative-control method check; a control with zero observations or inadequate block coverage is `not_assessable` and blocks replacement evidence rather than being treated as a passed check.

## Epoch protocol

`docs/a_short_evidence_epoch_mode_registry_20260725.json` registers the seventh track independently. `docs/a_short_theme_forward_comparison_epoch_20260725.json` owns its active epoch.

Before freeze, results are audit-only and do not count. The per-track registry is the sole mode authority; there is no global switch capable of arming all tracks. The runner's explicit `--start-epoch <id> --epoch-start-as-of <YYYYMMDD>` operation accepts only the latest complete Stage3 cohort while every H10 result is still unobserved. Friday capture may freeze a Monday decision cohort, but that cohort cannot count before Monday. Decision-time admission has a frozen three-calendar-day bounded recovery window; it is sealed only while H10 remains unobserved, reports eligible-but-unadmitted cohorts, and can never be retrofilled after that window.

Admission is atomic: persisted candidate count, exact five `final` rows, complete `final/watch` roles, finite `final_score`, seven policy inputs, internally consistent theme IDs/roles, return unit, decision/run/price clocks, runtime configuration fingerprint, and source fingerprints must all agree. The epoch freezes the complete schema-validated taxonomy registry, source/runtime configuration, governance, schemas, and semantic execution closure. Any drift stops its clock; reset archives the old epoch, starts from zero, and must use an ID never used by an archive or private receipt directory.

Decision-time admission receipts and later terminal H10 receipts are separate immutable chains under a provably gitignored `state/a_short/theme_forward_comparison_private/v1`; every terminal receipt binds its prior admission. Creation seals only a cohort whose H10 values are then unobserved. Validation reconstructs the same decision-time projection and re-runs that same builder with the receipt's recorded admission date, so later settlement cannot invalidate decision fields. **Trust boundary:** this local chain is not an independently timestamped proof against an operator who can rewrite both the private receipt directory and the epoch pointer; it is forward evidence only under the trusted-local-operator assumption. It must never be described as externally independently verified timing. A future external or committed-anchor design would be a separate authority change, not a silent strengthening of this component. **Accepted by the user on 2026-07-26** as the operating assumption for this track: no supported operation can back-date an admission (`admission_date` is supplied only by receipt validation; the weekly runner and both CLI paths always seal at real wall-clock time), so the clock is honest as long as the operator never hand-writes receipts into the private root. Weakening that assumption, or claiming stronger provenance, requires a new user decision. Missing, deleted, changed, or rolled-back evidence stops the epoch; a receipt written before its epoch manifest is durably committed is resumed only when exact bytes match. H10 independence uses complete per-row realized T+1 entry/H10 exit dates. Actual entered positions determine coverage; unfilled and limit-up-unbuyable slots are cash. At 24 sealed mature official-policy H10 weeks the output is preview-only. Once at least 36 sealed mature weeks exist, the only formal packet is computed from the first 36 sealed cohorts and their frozen order, even if the runner was unavailable in week 36. Archive, receipt, epoch pointer and registry publication are idempotent restartable transitions, so a crash cannot burn the one formal look. Later public packets retain the recorded verdict/hash instead of replacing or hiding it. Pure comments, line endings, and non-semantic JSON formatting do not change the contract fingerprint.

Frozen themes form an exploratory-only family. Theme rows use their own member-versus-nonmember non-overlap selection, explicitly marked `exploratory_theme_member_vs_nonmember_only`; that selection never feeds the seven policy-vs-primary evidence blocks, Holm family, deployability, or an action. Theme rows enforce minimum week/stock-week gates and report effect, interval, sample status, and a non-actionable exploratory verdict. New registry themes require a new epoch.

## Verdicts

Formal results use the frozen +0.25pp practical margin and Holm-adjusted two-sided practical test: `supported`, `harmful`, `not_practically_superior`, `underpowered`, `not_supported`, `not_deployable`, or `insufficient_evidence`. No result authorizes replacement. The negative control can issue `unexpected_benefit_method_validity_warning`, which blocks replacement recommendations for that epoch.
